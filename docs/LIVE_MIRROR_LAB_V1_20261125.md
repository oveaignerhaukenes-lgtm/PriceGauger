# LIVE Mirror Lab — validation before evolution

## Phase 1 (this PR)
- Read existing enabled + armed V3 instance boundaries and their stored configuration, capital policy, raw regime/STOP policy, modifier settings, account-value observations, last runtime heartbeat and genuine BBO. No bootstrap, Saxo calls, LIVE authority/config writes or AI calls.
- Register versioned reference twins in pg_live_mirror_registry_v1 from the separate LiveSimLab worker. Only that table is written. A configuration revision gets a distinct ID; inactive versions are retained. A re-activated identical configuration reuses its reference ID, not a simulated trading session.
- Readiness is deliberately explicit: WAIT_CONFIG, WAIT_ORDER_TRUTH, WAIT_FLAT_BASELINE, WAIT_ACCOUNT_BASELINE, WAIT_BBO, WAIT_CALIBRATION. Heartbeat inventory is not an exact contemporaneous broker read; account NAV is not cash-flow-adjusted return. Non-NOK or negative account values cannot seed the prototype.
- Pure virtual execution primitive accepts explicit calibration terms and observable BBO. Uses receipt time, bid for sells/ask for buys, adverse slippage, per-side fees, weighted entry basis, realized P/L and margin/capital model. Never flips across FLAT in one fill, never rejects reductions due to margin. Tested against synthetic scenarios only. No auto fills or results published yet.
- UI: Live-Sim Lab → LIVE Mirror Lab. Reference census only; no implied profitability or simulator parity.

## Remaining gates before independent forward trading
1. Capture actual source-time and receipt-time market evidence, exact account/position basis, broker instrument rules, currency conversion, cost and margin terms, decision key/time, order sent/ack/final fill and rejection reason, exact quantities. Existing execution-event timestamp is reconciliation time, not actual fill time; use verified final fills and never guess prices. Capture via bounded telemetry, not per-twin broker requests.
2. Use canonical V3 strategy registry/decision functions, separate strategy state and common feature calculations, virtual broker ledger with durable idempotent settlement; no copying LIVE orders or later LIVE account values into the simulated path. Start a distinct forward session only after an independently verified flat baseline and calibrated instrument terms. Config edits get a new session. Report unsupported modifiers/tick families rather than silently omit them. Preserve raw legacy policy context, including strategy-binding semantics of the running version.
3. Compare matched decision IDs and exact instrument/side/quantity, target divergence, timestamps, fill/slippage/cost, rejection class, inventory and cash-flow-adjusted net P/L. Separate strategy parity from execution parity. Include missing/unmatched events; avoid matching by closest timestamp alone. Use calibration and later untouched validation cohorts. Model transient broker failures probabilistically, not by copying known future rejects into forward SIM.
4. Only after validation: parallel 10/100/1000 models sharing immutable feed/features, benchmark CPU/DB, prospective holdout/walk-forward evaluation with cost and drawdown, no automatic LIVE promotion.

## Known limitations
No actual forward virtual orders in this phase; no calibrated broker terms, funding, partial fills, rate-limit model, or full V3 modifier parity. No claim of exact LIVE parity. Snapshot sources are sampled separately and may be inconsistent within a cycle; do not treat a snapshot as an atomic broker state. This is a foundation for instrumentation and subsequent independent forward engine, not a validated simulator. Existing LIVE and legacy LAB engines remain unchanged.
